**Reading the numbers.** Both servers and the load generator share this machine. Redis runs commands on one thread; my-redis uses every core, so compare *CPU per op* for efficiency and *ops/s* for capacity. *Cores* is server CPU time divided by wall time. If the load generator's cores approach the machine's CPU count, it is the bottleneck and ops/s understates both servers. Latency for raw scenarios is per pipelined batch.

## Observations

- Largest throughput gap: **PUBLISH to 50 subscribers (4 publishers, pipeline 16)** at 0.14x Redis.
- Closest to (or ahead of) Redis: **GET via Client (1 in flight)** at 1.26x.
- my-redis uses on average **22.6x** the CPU time per operation that Redis does across the summary scenarios; that is the efficiency gap to close independently of core count.
- **PING (raw, pipeline 16)**: my-redis on 1 thread does 586,800 ops/s at 1.70us CPU/op; on all threads 2,403,696 ops/s at 4.35us CPU/op using 10.4 cores. 2.6x the CPU per op for 4.10x the throughput points at contention between threads (the shared db lock, the scheduler) rather than command cost.
- **SET (raw, pipeline 16)**: my-redis on 1 thread does 528,678 ops/s at 1.89us CPU/op; on all threads 939,917 ops/s at 10.83us CPU/op using 10.2 cores. 5.7x the CPU per op for 1.78x the throughput points at contention between threads (the shared db lock, the scheduler) rather than command cost.
- **GET (raw, pipeline 16)**: my-redis on 1 thread does 543,587 ops/s at 1.84us CPU/op; on all threads 1,910,442 ops/s at 6.35us CPU/op using 12.1 cores. 3.5x the CPU per op for 3.51x the throughput points at contention between threads (the shared db lock, the scheduler) rather than command cost.
- With a single connection (no contention), my-redis needs 2.41us CPU per SET against Redis's 0.80us (3.0x): the per-request cost of parsing, allocating and writing replies.
- Each key with a 16 B value costs 186 B in my-redis and 93 B in Redis (2.0x).
- Pipelining from 1 to 64 multiplies my-redis throughput by 1.5x: the larger this is, the more time goes to per-request round trips and syscalls rather than command execution.

## Profiling next steps

- CPU profile the server under one scenario: `cargo build --release`, start `target/release/my-redis-server`, run `scripts/bench.sh --address 127.0.0.1:6379 --no-redis --quick --only set --duration 30`, and attach a sampling profiler to the server (`samply record -p <pid>` on macOS, `perf record -g -p <pid>` on Linux).
- Compare allocation counts with a heap profiler (`heaptrack`, or Instruments' Allocations on macOS) on the same run; a high *CPU per op* with low *cores* points at per-request allocation or syscalls rather than contention.
- `JSON` with every number is next to this report for tracking changes over time.
