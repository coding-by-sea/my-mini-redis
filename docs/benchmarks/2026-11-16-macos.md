**Reading the numbers.** Both servers and the load generator share this machine. Redis runs commands on one thread; my-redis uses every core, so compare *CPU per op* for efficiency and *ops/s* for capacity. *Cores* is server CPU time divided by wall time. If the load generator's cores approach the machine's CPU count, it is the bottleneck and ops/s understates both servers. Latency for raw scenarios is per pipelined batch.

## Observations

- Largest throughput gap: **PUBLISH to 50 subscribers (4 publishers, pipeline 16)** at 0.04x Redis.
- Closest to (or ahead of) Redis: **SET via Client (1 in flight)** at 0.78x.
- my-redis uses on average **55.3x** the CPU time per operation that Redis does across the summary scenarios; that is the efficiency gap to close independently of core count.
- **PING (raw, pipeline 16)**: my-redis on 1 thread does 477,290 ops/s at 2.10us CPU/op; on all threads 557,440 ops/s at 9.96us CPU/op using 5.5 cores. 4.8x the CPU per op for 1.17x the throughput points at contention between threads (the shared db lock, the scheduler) rather than command cost.
- **SET (raw, pipeline 16)**: my-redis on 1 thread does 443,466 ops/s at 2.26us CPU/op; on all threads 471,587 ops/s at 19.08us CPU/op using 9.0 cores. 8.5x the CPU per op for 1.06x the throughput points at contention between threads (the shared db lock, the scheduler) rather than command cost.
- **GET (raw, pipeline 16)**: my-redis on 1 thread does 453,194 ops/s at 2.21us CPU/op; on all threads 552,131 ops/s at 11.46us CPU/op using 6.3 cores. 5.2x the CPU per op for 1.22x the throughput points at contention between threads (the shared db lock, the scheduler) rather than command cost.
- With a single connection (no contention), my-redis needs 2.22us CPU per SET against Redis's 0.67us (3.3x): the per-request cost of parsing, allocating and writing replies.
- Each key with a 16 B value costs 271 B in my-redis and 88 B in Redis (3.1x).
- Pipelining from 1 to 64 multiplies my-redis throughput by 2.4x: the larger this is, the more time goes to per-request round trips and syscalls rather than command execution.

## Profiling next steps

- CPU profile the server under one scenario: `cargo build --release`, start `target/release/my-redis-server`, run `scripts/bench.sh --address 127.0.0.1:6379 --no-redis --quick --only set --duration 30`, and attach a sampling profiler to the server (`samply record -p <pid>` on macOS, `perf record -g -p <pid>` on Linux).
- Compare allocation counts with a heap profiler (`heaptrack`, or Instruments' Allocations on macOS) on the same run; a high *CPU per op* with low *cores* points at per-request allocation or syscalls rather than contention.
