**Reading the numbers.** Both servers and the load generator share this machine. Redis runs commands on one thread; my-redis uses every core, so compare *CPU per op* for efficiency and *ops/s* for capacity. *Cores* is server CPU time divided by wall time. If the load generator's cores approach the machine's CPU count, it is the bottleneck and ops/s understates both servers. Latency for raw scenarios is per pipelined batch.

## Observations

- Largest throughput gap: **PUBLISH to 50 subscribers (4 publishers, pipeline 16)** at 0.17x Redis.
- Closest to (or ahead of) Redis: **GET via Client (1 in flight)** at 0.77x.
- my-redis uses on average **35.0x** the CPU time per operation that Redis does across the summary scenarios; that is the efficiency gap to close independently of core count.
- **PING (raw, pipeline 16)**: my-redis on 1 thread does 1,429,984 ops/s at 0.70us CPU/op; on all threads 1,174,627 ops/s at 11.77us CPU/op using 13.8 cores. 16.9x the CPU per op for 0.82x the throughput points at contention between threads (the shared db lock, the scheduler) rather than command cost.
- **SET (raw, pipeline 16)**: my-redis on 1 thread does 1,153,914 ops/s at 0.87us CPU/op; on all threads 583,974 ops/s at 24.10us CPU/op using 14.1 cores. 27.8x the CPU per op for 0.51x the throughput points at contention between threads (the shared db lock, the scheduler) rather than command cost.
- **GET (raw, pipeline 16)**: my-redis on 1 thread does 1,250,131 ops/s at 0.80us CPU/op; on all threads 1,031,382 ops/s at 13.50us CPU/op using 13.9 cores. 16.9x the CPU per op for 0.83x the throughput points at contention between threads (the shared db lock, the scheduler) rather than command cost.
- With a single connection (no contention), my-redis needs 1.17us CPU per SET against Redis's 0.71us (1.6x): the per-request cost of parsing, allocating and writing replies.
- On my-redis, subscribers fall behind during **PUBLISH to 50 subscribers (4 publishers, pipeline 16)**: median delivery latency is 1.44s while a publish takes 1.52ms, and server memory grew by 273.6 MiB of queued messages. The server accepts publishes faster than it can write them to subscribers.
- Each key with a 16 B value costs 271 B in my-redis and 88 B in Redis (3.1x).
- During **PING (raw, pipeline 16)** on my-redis, server and load generator together used 15.6 of 18 cores: the machine was close to saturated, which also slows the generator.
- During **SET (raw, pipeline 16)** on my-redis, server and load generator together used 16.0 of 18 cores: the machine was close to saturated, which also slows the generator.
- During **GET (raw, pipeline 16)** on my-redis, server and load generator together used 16.2 of 18 cores: the machine was close to saturated, which also slows the generator.
- During **PUBLISH, no subscribers (raw, pipeline 16)** on my-redis, server and load generator together used 16.2 of 18 cores: the machine was close to saturated, which also slows the generator.
- During **PUBLISH to 50 subscribers (4 publishers, pipeline 16)** on my-redis, server and load generator together used 16.6 of 18 cores: the machine was close to saturated, which also slows the generator.
- Pipelining from 1 to 64 multiplies my-redis throughput by 2.9x: the larger this is, the more time goes to per-request round trips and syscalls rather than command execution.

## Profiling next steps

- CPU profile the server under one scenario: `cargo build --release`, start `target/release/my-redis-server`, run `scripts/bench.sh --address 127.0.0.1:6379 --no-redis --quick --only set --duration 30`, and attach a sampling profiler to the server (`samply record -p <pid>` on macOS, `perf record -g -p <pid>` on Linux).
- Compare allocation counts with a heap profiler (`heaptrack`, or Instruments' Allocations on macOS) on the same run; a high *CPU per op* with low *cores* points at per-request allocation or syscalls rather than contention.
- `JSON` with every number is next to this report for tracking changes over time.
